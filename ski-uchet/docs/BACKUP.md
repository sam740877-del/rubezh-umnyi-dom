# Резервные копии: как снимаются и как вернуть базу

Этот файл существует потому, что **копия без описанного пути возврата — дыра**.
В день аварии человек остаётся с папкой копий и без инструкции, а соображать
приходится в худший момент из возможных.

---

## Где лежат копии

По умолчанию — папка `backups` рядом с программой. Переопределяется переменной
окружения `SKI_BACKUP_DIR`:

```
SKI_BACKUP_DIR=D:\Копии\СКИ
```

Имя файла: `ski_backup_2026-09-06_154312.db` — дата и время снятия.
Хранятся последние 30 копий, старые удаляются сами.

## Как снимаются

**Из системы:** раздел «Копии» (виден администратору) → кнопка «Снять копию сейчас».

**Что происходит при этом:**

1. Копия снимается штатным механизмом SQLite. Файл базы **не копируется** —
   это дало бы копию в середине чужой транзакции.
2. Копия сразу проверяется по содержимому (`PRAGMA integrity_check`).
3. **Повреждённая копия удаляется** и за успешную не считается. Так и должно
   быть: копия, которая выглядит целой, но не открывается, — худший отказ
   из возможных, потому что о нём узнают в момент восстановления.

## Как вернуть базу из копии

Кнопки «Восстановить» в системе **нет намеренно**. Восстановление затирает всё,
что накопилось после снятия копии, — такое делают руками, понимая, что теряют.

### Порядок

1. **Остановите сервер.** Иначе восстановленную базу тут же перезапишет
   работающая система.

2. **Сохраните текущую базу**, даже если считаете её испорченной:

   ```
   ren ski.db ski.db.before-restore
   ```

   Это не формальность. Если в копии не окажется того, что вы ищете,
   вернуться будет некуда.

3. **Проверьте копию до того, как на неё положились.** Откройте её любым
   просмотрщиком SQLite или выполните:

   ```
   sqlite3 backups\ski_backup_2026-09-06_154312.db "PRAGMA integrity_check;"
   ```

   Ответ должен быть `ok`.

4. **Поставьте копию на место базы:**

   ```
   copy backups\ski_backup_2026-09-06_154312.db ski.db
   ```

5. **Запустите систему** и убедитесь, что данные на месте: откройте сводку,
   посмотрите число приборов и последние записи в журнале движения.

6. **Только убедившись — удалите** `ski.db.before-restore`.

### Что при этом теряется

Всё, что произошло **после** снятия копии: выдачи, возвраты, поверки, заявки,
приложенные документы. Копии снимаются раз в сутки, значит потерять можно
до суток работы.

**Файлы вложений не входят в копию** — они лежат в папке `storage` отдельно.
Её копируйте своими средствами вместе с базой, иначе после восстановления
записи о документах останутся, а самих файлов не будет.

## Что делать, если система предупреждает о молчании копий

Сообщение «Резервных копий нет ни одной» или «Последняя копия сделана N дней
назад» означает, что система работала, а копия не создалась. Само это
не исправится. Проверьте по порядку:

| Что проверить | Как |
|---|---|
| Существует ли папка копий | откройте путь из `SKI_BACKUP_DIR` |
| Есть ли место на диске | копия весит примерно столько же, сколько база |
| Есть ли права на запись | попробуйте создать в папке файл вручную |
| Доступен ли сетевой диск | если папка на сервере — он может быть отключён |

---

## Что будет после переезда на PostgreSQL

Механизм сменится: вместо SQLite Online Backup API будет `pg_dump`, а проверка
целостности — пробным восстановлением в отдельную базу. **Правила останутся
те же:** копия проверяется по содержимому, состояние читается фактом по диску,
молчание — тревога.

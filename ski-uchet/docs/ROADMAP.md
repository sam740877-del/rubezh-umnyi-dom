# План работ

Проект: система учёта средств контроля и измерений (СКИ) для строительного контроля.
Документ живой — правим по ходу.

---

## Где мы сейчас

**Этап 0 — ядро системы. Готово.**

Работающее приложение с базой данных: реестр приборов, договоры и участки, комплект
по договору с автоматической сверкой «требуется → факт», поверки с расчётом сроков,
журнал выдачи и возврата, выгрузки CSV, 26 тестов.

Интерфейс на текущий момент принят как верный, дорабатываем по ходу.

Что уже зашито в логику:

- прибор нельзя выдать на второй участок, пока не оформлен возврат;
- прибор в ремонте, на поверке или списанный выдать нельзя;
- прибор с просроченной поверкой выдать нельзя — только с явной отметкой;
- брак по поверке снимает прибор с участка и отправляет в ремонт;
- срок поверки считается автоматически по межповерочному интервалу типа.

## Этап 1. Перенос реальных данных и запуск в работу

**Цель:** система заполнена настоящим парком приборов и запускается на рабочем
компьютере без команд в терминале.

- Импорт существующего реестра приборов из Excel (нужен файл — вопрос 23).
- Настройка справочника типов под реальную номенклатуру и ваши межповерочные
  интервалы (вопрос 15).
- Заведение действующих договоров, участков и комплектов по ним.
- Запуск ярлыком с рабочего стола, без терминала (вопрос 27).
- Настройка резервного копирования базы (вопрос 28).

**Блокирует:** ответы на вопросы 23, 26, 27, 15.

## Этап 2. Документы для заказчика

**Цель:** из системы печатаются те бумаги, которые сейчас делаются руками.

- Акт приёма-передачи приборов на участок — печать из карточки участка (вопрос 18).
- Перечень СИ, применяемых на объекте, со сроками поверки — для заказчика (вопрос 19).
- Журнал учёта СИ по вашей форме (вопрос 20).
- Справочник материально ответственных лиц вместо текстового поля (вопрос 21).

**Блокирует:** формы документов, вопросы 18-22.

## Этап 3. Метрология вглубь

**Цель:** поверка перестаёт быть строчкой в таблице и становится управляемым процессом.

- Вложения к поверке: сканы и фото свидетельств (вопрос 12).
- Заявки на поверку: что отправлено, кому, когда ждём назад, сколько стоило (вопрос 13).
- График поверок на год вперёд с бюджетом по месяцам (вопрос 17).
- Настраиваемый горизонт предупреждения вместо жёстких 30 дней (вопрос 16).

## Этап 4. Несколько пользователей

**Цель:** с системой работает не один человек, и видно, кто что сделал.

- Учётные записи и роли: кладовщик, инженер строительного контроля, руководитель.
- Журнал действий: кто выдал, кто изменил карточку, кто удалил позицию.
- Работа по локальной сети офиса или через интернет с объектов.
- При выходе за пределы одного компьютера — переезд на PostgreSQL
  (код к этому готов, меняется строка подключения).

**Блокирует:** вопросы 1, 2, 26.

## Этап 5. Уведомления и аналитика

- Напоминания о заканчивающихся поверках: почта или Telegram (вопрос 29).
- Дашборд: загрузка парка, затраты на поверки по годам, хронический дефицит
  по типам приборов (вопрос 32).
- Учёт ремонтов и затрат на них (вопрос 31).

## Этап 6. Работа с объекта

- QR-коды на приборы: наклейка, сканирование телефоном при выдаче и возврате (вопрос 30).
- Упрощённый мобильный интерфейс для прораба: посмотреть комплект, отметить возврат.

---

## Порядок и приоритеты

Этапы 1 и 2 — основные: они дают реальную пользу сразу, потому что закрывают
ручную работу, которая делается прямо сейчас. Этапы 3-6 набирают ценность
по мере того, как система обрастает данными.

Порядок можно менять. Если, например, заказчик требует перечень СИ уже на этой неделе —
двигаем этап 2 вперёд.

## Принятые технические решения

| Решение | Почему |
|---|---|
| Python + FastAPI, веб-интерфейс в браузере | работает на любом компьютере и с планшета в сети, не требует установки клиента |
| SQLite, база — один файл | бэкап копированием файла, не нужен сервер БД; при переходе на несколько офисов меняется одна строка подключения |
| Всё локально, без облака | данные по договорам не уходят наружу |
| Правила учёта в коде, а не в инструкции | нельзя «случайно» выдать прибор с просроченной поверкой |
| Интерфейс на русском, термины предметной области | пользуются прорабы и кладовщики, а не программисты |

## Риски

- **Данные не перенесут.** Если импорт из Excel окажется сложным, система останется
  пустой и ей не будут пользоваться. Решение — этап 1 в приоритете, импорт делаем
  под реальный файл.
- **Расхождение с бумажным документооборотом.** Если акт из системы не совпадёт
  с формой, которую принимает заказчик, будут вести и то и другое. Решение — нужны
  реальные формы документов (вопрос 18).
- **Один пользователь на всех.** Пока нет ролей, любой может изменить любую запись.
  Приемлемо для одного-двух человек, дальше нужен этап 4.

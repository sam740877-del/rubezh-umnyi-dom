## Где мы сейчас

**Этап 0 — ядро системы. Готово.**

Работающее приложение с базой данных: реестр приборов, договоры и участки, комплект
по договору с автоматической сверкой «требуется → факт», поверки с расчётом сроков,
журнал выдачи и возврата, выгрузки CSV, 26 тестов. Интерфейс принят как верный,
правим по ходу.

Правила учёта зашиты в код:

- прибор нельзя выдать на второй участок, пока не оформлен возврат;
- прибор в ремонте, на поверке или списанный выдать нельзя;
- прибор с просроченной поверкой выдать нельзя — только с явной отметкой;
- брак по поверке снимает прибор с участка и отправляет в ремонт;
- статус «на участке» ставится только через операцию выдачи.

## Что изменилось после ответов 05.09

Ответы заказчика меняют не сроки, а устройство системы:

1. **Не один компьютер, а сервер в интернете.** SQLite и «всё локально» отменяются:
   нужен PostgreSQL, домен, HTTPS. Этап с авторизацией поднят с четвёртого места
   на второе — встраивать вход и роли в наполненную базу дороже, чем заложить сразу.
2. **Роли, включая мастеров участков.** Нужны разграничение видимости (мастер видит
   свой участок, а не весь парк) и журнал действий. Работа с телефона перестаёт быть
   пунктом «на вырост» — это рабочий сценарий мастера.
3. **Сканы не только по поверкам.** Вложения делаем общим механизмом: файл можно
   приложить к прибору, к поверке, к акту выдачи, к договору.
4. **Комплекты повторяются и закреплены приложением к договору.** Нужны шаблоны
   типовых комплектов и реквизиты приложения в карточке участка.
5. **Заявки с согласованием.** Мастер не перемещает приборы сам — он подаёт заявку,
   а её согласует начальник. Это не настройка прав, а отдельный механизм: заявка,
   решение по ней, история. В первоначальном плане его не было.

## Сделано сверх этапа 0 (05.09)

- **Заявки на перемещение** с согласованием главным инженером и обязательным
  комментарием при отказе; согласование сразу исполняет перемещение.
- **Типовые комплекты** — собираются один раз, применяются к участку одним нажатием.
- **Реквизиты приложения к договору** в карточке участка.

Роли и вход не делались — это этап 2.

## Этап 1. Данные и справочники

**Цель:** система заполнена настоящим парком приборов, комплекты собираются из шаблонов.

- Импорт реестра приборов из Excel (файл в понедельник). Инвентарные номера
  в реестре уникальны — импорт может опираться на них как на ключ.
- Историю поверок не переносим: берём текущее состояние по каждому прибору.
- Межповерочный интервал заполняется из паспорта прибора, а не из описания типа.
- Справочник типов под вашу номенклатуру. Учитываем только средства измерений,
  все приборы свои — арендованных и чужих в модели не нужно.

**Ждёт:** файл реестра.

## Этап 2. Сервер, доступ через интернет и роли

**Цель:** система живёт в сети, у каждого свой вход со своими правами.

- Переезд на PostgreSQL — файловая база не держит нескольких пользователей через интернет.
- Сервер, домен, HTTPS-сертификат.
- Вход по логину и паролю с восстановлением по почте; СМС отклонён.
- Роли: администратор, инженер СК, кладовщик, мастер участка, согласующий.
- Разграничение видимости: мастер работает только со своим участком.
- Заявки на перемещение: мастер подаёт, начальник согласует или отклоняет,
  решение и его автор остаются в истории прибора.
- Журнал действий: кто выдал, кто изменил, кто удалил.
- Автоматические резервные копии на сервере.

**Ждёт ответов:** 41, 42, 43, 45.

## Порядок

Этапы 1 и 2 идут первыми по разным причинам. Первый — потому что пустой системой
не пользуются. Второй — потому что вход, роли и серверная база это фундамент:
пристроить их к наполненной базе дороже, чем заложить сразу. Третий этап двигаем
вперёд, если заказчик потребует перечень СИ раньше.

## Технические решения

| Решение | Почему |
|---|---|
| Python и веб-интерфейс в браузере | работает и на компьютере, и с телефона мастера |
| PostgreSQL на сервере *(пересмотрено 05.09)* | планировался файл SQLite, но доступ через интернет и несколько одновременных пользователей файловая база не держит |
| Сервер в интернете, вход по логину *(пересмотрено 05.09)* | с объектов нужен доступ — значит, нужна и защита |
| Правила учёта в коде | нельзя «случайно» выдать прибор с просроченной поверкой |
| Русский интерфейс, термины отрасли | пользуются кладовщики и мастера, а не программисты |
| Роли: администратор, инженер СК, кладовщик, мастер участка, согласующий *(уточнено 05.09)* | мастер видит только свой участок и не перемещает приборы сам — только через заявку |
| Сервер конторы *(уточнено 05.09)* | у компании есть свой надёжный сервер — размещаем на нём, персональные данные остаются под контролем компании |
| Вход только по паролю, без СМС *(05.09)* | СМС-шлюз это абонентская плата плюс деньги за сообщение, при 5-15 пользователях не окупается |

## Риски

- **Персональные данные на сервере в интернете.** В системе будут ФИО и должности
  сотрудников. Если сервер арендуется за рубежом — это нарушение требования хранить
  персональные данные россиян в России. Поэтому вопрос 33 блокирующий.
- **Данные не перенесут.** Если импорт из Excel окажется сложным, система останется
  пустой. Импорт пишем под реальный файл, а не под выдуманный формат.
- **Расхождение с бумажным документооборотом.** Если акт из системы не совпадёт
  с утверждённой формой, будут вести и то и другое.
- **Сервер снят с повестки как риск:** у конторы есть свой надёжный сервер.
  Осталось уточнить операционную систему и кто его обслуживает — вопросы 47 и 48.
- **Мастера не станут пользоваться.** Если мастеру придётся продираться через полный
  интерфейс кладовщика, он вернётся к звонкам в офис. Отсюда отдельный мобильный сценарий.

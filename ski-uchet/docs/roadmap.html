Где мы сейчас

Этап 0. Ядро системы — готово

Работающее приложение с базой данных: реестр приборов по инвентарным номерам, договоры и участки, комплект по договору с автоматической сверкой «требуется → факт», поверки с расчётом сроков по межповерочному интервалу, журнал выдачи и возврата, выгрузки в Excel. Интерфейс принят как верный, правим по ходу работы.

Правила учёта зашиты в программу, а не в инструкцию — обойти их случайно нельзя:

  • прибор нельзя выдать на второй участок, пока не оформлен возврат;
  • прибор в ремонте, на поверке или списанный выдать нельзя;
  • прибор с просроченной поверкой выдать нельзя — только с явной отметкой;
  • брак по поверке снимает прибор с участка и отправляет в ремонт;
  • статус «на участке» ставится только через операцию выдачи, руками — никак.

Принятые технические решения

РешениеПочему так
Python и веб-интерфейс в браузере работает на любом компьютере и с планшета в сети, не нужно ставить клиент на каждую машину
База — один файл SQLite резервная копия делается копированием файла; при переходе на несколько офисов меняется одна строка подключения
Всё локально, без облака данные по договорам не уходят наружу
Правила учёта в коде нельзя «случайно» выдать прибор с просроченной поверкой
Русский интерфейс, термины отрасли пользуются кладовщики и прорабы, а не программисты

Риски

  • Данные не перенесут Если импорт из Excel окажется сложным, система останется пустой и ей не будут пользоваться. Поэтому этап 1 в приоритете, а импорт пишем под ваш реальный файл, а не под выдуманный формат.
  • Расхождение с бумажным документооборотом Если акт из системы не совпадёт с формой, которую принимает заказчик, будут вести и то и другое. Нужны реальные формы документов — вопрос 18.
  • Один доступ на всех Пока нет ролей, любой может изменить любую запись. Для одного-двух человек это приемлемо, дальше нужен этап 4.
